# Автоплан и обновление интерфейса — дизайн

_Черновик от 19 ноября 2026. Источник для реализации в Claude Code: «реализуй этап N по `docs/AUTOPLAN.md`»._
_После каждого этапа — как обычно: документ бизнес-логики, `docs/REVIEW.md`, `CLAUDE.md`._

## 0. Зачем

Функционально приложение покрывает всё (план → покупки → запасы → готовка → КБЖУ → деньги), но **дорого во вводе**:
каждое блюдо, порция и вес — руками. Цель — чтобы приложение **само предлагало** план и покупки, а человек только
правил. Ручное заполнение и правка плана остаются полностью как сейчас.

Решение — слой поверх текущей модели (бэкенд не переписываем) + обновление интерфейса. Без LLM: правила,
автономно, тестируемо.

## 1. Как живём (вводные от семьи)

- Готовим **почти каждый день**; иногда — на день-два вперёд.
- Делаем **заготовки в морозилку** (котлеты и т. п.) — выручают в дни без готовки.
- **Завтраки** чаще готовим (каша, сырники, яичница, омлет), иногда — из готовых продуктов (бутерброды).
- Блюд в ротации ~10–20, повседневные — простые; «эдакое» — изредка, по настроению.
- Готовые продукты помимо основной еды из недели в неделю почти одни и те же.
- Проблемы: перерасход, выброшенные остатки, лишние покупки в доставке, много снеков/сладкого.

Следствие: **единица планирования — небольшая закладка на 1–2 дня**, а не кастрюля на неделю.
Автоматически заполняться могут **любые приёмы пищи**.

## 2. Принцип сосуществования с ручным планом

- `MealItem.origin`: `manual` | `auto`. Новое из UI и всё существующее — `manual`.
- `MealItem.pinned` — «📌 закреплено».
- «Предложить неделю/дни» заполняет **только пустые ячейки** выбранного периода.
- Повторная генерация заменяет только `auto`, **не закреплённые**, без кастрюли (`cooking_log_id`) и без съеденных порций.
- Любая ручная правка `auto`-блюда (блюдо, порции, перенос) → оно становится `manual`.
- «Принять» (блюдо / день / неделю) → `manual` (снимает пометку черновика).
- У `auto`-блюда хранится причина выбора (`MealItem.auto_reason`, короткий текст или JSON):
  «не готовили 12 дн», «кабачок до 21.11», «общий товар с борщом», «заготовка в морозилке».

## 3. Данные

### 3.1. Рецепт (`Recipe`)
| Поле | Смысл | По умолчанию |
|---|---|---|
| `in_rotation` | участвует в автоплане | `true` |
| `effort` | `easy` / `special` | `easy` |
| `meal_types` | JSON-список приёмов пищи, где уместно | все |
| `keeps_days` | сколько дней можно есть одну закладку | 2 |
| `is_freezable` | можно заготовить в морозилку | `false` |

### 3.2. Заготовки в морозилке
Кастрюля (`RecipeCookingLog`) с признаком `is_frozen` и сроком `keeps_until` (по умолчанию +60 дней).
Резерв, «съел», остаток — существующей механикой. Автоплан ставит заготовку в дни, отмеченные «без готовки»,
или когда ей скоро истекает срок. Действие «Заморозить остаток» у обычной кастрюли (переводит в заготовку).

### 3.3. Настройки планировщика (`Household` или отдельная таблица `planner_settings`)
- какие приёмы пищи заполнять (по умолчанию все);
- дни «без готовки» (например, пятница) и дни для `special` (например, суббота) — по дням недели;
- макс. «эдаких» блюд в неделю;
- квота на снеки/сладкое, ₽/неделю, и категории, которые считаются снеками;
- веса оценки (п. 4.2) — с разумными значениями по умолчанию, в UI не обязательно.

### 3.4. Отзывы (`plan_feedback`)
`household_id, recipe_id | item_key, action (replaced | removed | pinned | accepted), created_at`.

### 3.5. Типичная порция — без новой таблицы
Медиана съеденных `MealPortion.weight_g` по (член семьи, рецепт / товар) за ~90 дней.
Нет истории → по рецепту у других членов семьи пропорционально цели ккал → доля цели ккал на приём пищи
(завтрак 25 %, обед 35 %, ужин 30 %, перекус 10 %).

### 3.6. Регулярные готовые продукты
`HouseholdProduct.regular`: `auto` (решает статистика) | `always` | `never`; `regular_qty` — ручное количество в неделю.

## 4. Алгоритм автоплана (`app/services/autoplan.py`)

### 4.1. Шаги
1. **Остатки и заготовки.** Пустые ячейки сначала закрываются тем, что стоит в холодильнике (резерв с учётом
   `keeps_days`/срока), затем заготовками, если день «без готовки» или им скоро истекает срок.
2. **Регулярные приёмы.** Из истории `MealItem` с `variant_id`: продукт в ячейке (приём пищи) встречался в ≥ 50 %
   недель за последние 8 → ставится туда же как `auto` (бутерброды, йогурт на перекус).
3. **Готовки.** Для оставшихся ячеек по дням: выбрать блюдо по оценке (4.2) с учётом `meal_types`,
   `effort`/дней `special`; блюдо закрывает ячейку готовки и следующие в пределах `keeps_days` и выхода
   закладки. Одно блюдо не ставится на два приёма одного дня. Завтраки — отдельный пул (`meal_types`).
4. **Пересчёт** оценок после каждого выбора (пересечения, бюджет, разнообразие).
5. **Порции** — типичные (3.5); вес закладки и покупки считаются существующими правилами (целые закладки,
   `allow_half`, допуск семьи).

### 4.2. Оценка блюда
```
score = w_rest   * min(дней_с_последней_готовки / 14, 1)
      + w_expiry * доля_ингредиентов_из_запасов_со_сроком_≤3_дней
      + w_share  * доля_товаров_общих_с_уже_выбранными_на_период
      - w_cost   * max(0, (цена_порции − средняя) / средняя), если остаток бюджета мал
      + w_kbju   * насколько_закрывает_недобор_цели (белок, ккал) у едоков
      + w_fb     * отзывы (pinned/accepted +, replaced/removed −, затухание ~30 дней)
      − штраф, если то же блюдо уже есть в последние 2 дня
```
Детерминированность: при равенстве — по id; для 🔄 «другой вариант» — следующий по оценке, без повторов.
Цена порции и бюджет — из `app/services/finance.py`.

### 4.3. API (черновик)
- `POST /plan/autofill` `{start, end, meal_types?, dry_run?}` → созданные/заменённые блюда с причинами.
- `POST /plan/items/{id}/alternative` → следующий вариант на ту же ячейку.
- `POST /plan/items/{id}/accept`, `POST /plan/accept` `{start, end}`.
- `PATCH /plan/items/{id}` с `pinned`.
- `GET/PATCH /household/planner` — настройки.

## 5. Покупки: «Регулярное» и квота снеков

- Раздел «Регулярное» в активном списке: товары, купленные в ≥ 50 % недель за 8 недель (по партиям-покупкам
  и чекам), количество — медиана в неделю, минус запасы. `always`/`never` переопределяют. Строки ведут себя как
  ручная добавка (`added`): переживают «Пересчитать».
- Снеки: «потрачено N из квоты» в покупках и в «Деньгах»; сверх квоты товары категории в «Регулярное» не попадают.

## 6. Интерфейс

### 6.1. Новое для автоплана (на текущем фронтенде)
- План: кнопка «✨ Предложить» (неделя / выбранные дни); `auto`-блюда — пунктирная рамка, причина мелким
  текстом; действия 📌 / 🔄 / ✕ / ✓; «Принять всё».
- Рецепт: «в ротации», простое/эдакое, приёмы пищи, сколько дней хранится, можно замораживать.
- Холодильник: «❄️ Заморозить остаток», заготовки отдельным блоком.
- Семья → «Планировщик»: настройки 3.3.
- Покупки: раздел «Регулярное», полоска квоты снеков.

### 6.2. Обновление интерфейса (отдельный этап)
- Переход на **Vite + TypeScript**, API-клиент из OpenAPI (FastAPI отдаёт схему); компоненты переносятся,
  не переписываются с нуля. Нужен Node на машине.
- Пересборка главных сценариев вокруг «меньше ввода»: экран «Сегодня» (что есть, что готовить, отметить «съел»
  одним касанием типичной порцией), план-неделя как черновик для правки, покупки.
- Перед этим этапом — короткий аудит экранов (что используется, что нет) и визуальная система; для визуальной
  части в Claude Code можно подключить плагин `frontend-design`. Текущие правила UI (модалки, `Picker`,
  `ProductFinder`) из `CLAUDE.md` — сохранить или осознанно заменить.

### Сделано на этапе 1 (отличия от черновика)
- `Recipe.meal_types = NULL` — любой приём пищи (как в черновике; решение Ивана 19.11). Чтобы суп не шёл на завтрак,
  у рецепта отмечаются уместные приёмы.
- Типичная порция без истории: перед долей цели ккал — порция рецепта (выход / порций, если порций > 1) × цель / 2000.
- Заготовки из морозилки предлагаются, если им осталось ≤ 14 дней (дни «без готовки» — с настройками на этапе 2).
- Срок свежей кастрюли: `good_until` = день готовки + `keeps_days` − 1; «Достать из морозилки» даёт новый срок от сегодня.
- `POST /plan/autofill` на этапе 1 — только шаг 4.1.1; отдаёт список предложений (`dry_run` — без записи).

### Сделано на этапе 2 (отличия от черновика)
- Настройки — таблица `planner_settings` (миграция `0023`): `meal_types`, `no_cook_days`, `special_days`,
  `max_special_per_week` (по умолчанию 1). Квота снеков — с этапом 3.
- Остаток закладки ставится в **тот же приём** следующих дней (решение Ивана 19.11), пока хватает выхода
  (`estimated_cooked_weight`) без допуска и не вышли `keeps_days`; причина — «та же закладка от DD.MM».
- `meal_types = NULL` — любой приём, в т. ч. завтрак и перекус (решение 19.11); ненужные приёмы выключаются
  в «Планировщике».
- «Эдакое»: не больше `max_special_per_week` за ISO-неделю (считая ручной план); если отмечены дни для него —
  только в эти дни (+0,5 к оценке).
- Веса: давно не готовили 1,0; срок ≤ 3 дней 0,8; общие товары 0,4 (только с другими блюдами); цена 0,5 (если
  траты месяца / бюджет > прошедшая доля месяца); белок 0,3 (доля ккал из белка против целей едоков, по умолч. 15 %);
  повтор за 2 дня −1. Причина — истекающий продукт, если есть, иначе самая весомая составляющая.
- Перегенерация удаляет прежние предложения выбранных приёмов (auto, без 📌, без кастрюли и съеденного) и
  подбирает заново; `AutofillOut.replaced` — сколько. `cook=false` — только остатки и заготовки («🧊 Только остатки»).
- 🔄 — следующий по оценке рецепт по кругу; «та же закладка» на следующие дни заменяется вместе с блюдом.
  Работает и для ручного блюда (если оно не приготовлено и не съедено); новое блюдо — auto.
- «Убрать» предложения в UI — удаление auto без 📌 по одному (отдельного эндпоинта нет).

### Ответы на вопросы этапа 3 (19.11)
- «Регулярное» в покупках — **предлагать блоком** («Обычно берём» с «+» и «Добавить всё»), не добавлять само.
- Регулярные готовые продукты в плане — в пустые ячейки и **добавкой к auto-блюду** (блюдо + хлеб), если так
  бывало в истории; ручные ячейки не трогаем.
- Снеки — категории выбирает семья в «Планировщике» (+ отметка «снек» у товара).

### Сделано на этапе 3 (отличия от черновика)
- Миграция `0024`: `HouseholdProduct.regular` (auto/always/never), `regular_qty`, `is_snack`;
  `PlannerSettings.snack_categories` (id категорий продуктов), `snack_quota` (₽ в неделю, NULL — без квоты).
- «Обычно берём» — `GET /shopping-list/regular?start_date&end_date`: окно — 8 полных недель до текущей, покупки
  (партии purchase/manual, в т. ч. из чеков); «обычно» — покупали в ≥ 4 неделях. В неделю — медиана сумм по неделям с
  покупкой (или `regular_qty`); на период — × число недель (округление, не меньше 1) − свободные запасы − неотмеченные
  строки активного списка. Округление до упаковок — как в списке. Базовые и never — не предлагаем; always — всегда.
  В список — существующим `POST /shopping-lists/{id}/lines` (строка как ручная добавка, переживает «Пересчитать»).
- Квота снеков: потрачено с понедельника по сегодня на снеки (категории семьи или «снек» у товара) + оценка
  предлагаемого ≤ квоты, иначе товар не предлагается (`snacks.hidden`). В «Деньгах» — `snack_spent` за период.
- Регулярные продукты в плане (шаг 4.1.2): по плану 8 недель до периода (ручное и съеденное; непринятые предложения
  не считаются) — товар в том же дне недели и приёме ≥ 4 недель. «Сам по себе» (в ячейке не было блюда) — в пустую
  ячейку до готовок; «к блюду» — добавкой к ячейкам, куда автоплан поставил блюдо в этом подборе. Порции — медиана
  по тем, кто ел его хотя бы в половине случаев. Причины: «обычно на перекус по четвергам», «обычно к обеду по …».

### Сделано на этапе 4 (отличия от черновика)
- Таблица `plan_feedback` (миграция `0026`): `recipe_id` или `item_key` (готовый продукт), `meal_type`, `action`
  (accepted | pinned | replaced | removed), `created_at`. Пишется только о предложениях (`origin = auto`):
  ✓ (и «Принять всё» — по разу на рецепт/товар), 📌 (закрепили), 🔄 (о прежнем рецепте), ✕ (убрали несъеденное).
  Ручной план, ручная правка предложения и перегенерация — не отзывы.
- Вес: 📌 +1, ✓ +0,5, 🔄 −0,7, ✕ −1; затухание вдвое за 30 дней, учитываются 120 дней; одинаковые отзывы об одном
  за день — один; сумма в пределах ±2. В оценке блюда — `W_FB = 0,5 × сумма`; причина «семья часто выбирает».
- Обычные готовые продукты (шаг 2), решение Ивана 19.11 — мягче: сумма отзывов ≤ −1,5 (два «убрать» в разные дни) —
  реже (свой день недели — через неделю, привычка — через день, причина «(реже: вы его убирали)»); ≤ −3 (ещё два) —
  не ставим. У товаров потолок суммы ±4, у рецептов ±2.
- «Любимое» (по просьбе Ивана 19.11): в скольких из 8 последних недель рецепт был в плане (ручное и съеденное) —
  `W_POP = 0,6 × доля`, причина «часто готовите». Разнообразие сохраняется: через неделю после последнего раза любимое
  ещё уступает новому блюду, через 3 дня и больше — обгоняет.
- Привычка «каждый день»: готовый продукт в этом приёме пищи ≥ 4 дней в неделю в среднем (по сроку истории, не больше
  8 недель) — предлагается каждый день, причина «обычно на перекус»; правило «тот же день недели» для него не нужно.
- 🔄 не возвращает рецепт, который сегодня уже заменили в этом приёме пищи, пока есть другие варианты.
- Отзывы переезжают при вступлении в семью.

## 8. Решённые вопросы (19.11)
- Дни «без готовки» и дни для «эдакого» — по умолчанию не заданы, семья отмечает сама в «Семья → Планировщик».
- Квота снеков — по умолчанию выключена; в «Деньгах» видно, сколько ушло на снеки за неделю.
- Генерация «на завтра» по вечернему уведомлению (PWA push) — после этапа 2, если кнопки окажется мало.
