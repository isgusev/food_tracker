# Food Tracker: разбор и план развития

_Ревью от 7 октября 2026, ветка `feature/web-ui`._

## 1. Что приложение умеет сейчас

| Блок | Возможности |
|---|---|
| **Продукты** | Общий справочник: категория → бренд → производитель → **версии КБЖУ** (новая версия не ломает старые рецепты, есть откат). Проверка согласованности ккал с БЖУ по Атвотеру (флаг `wrong_nutrients`). |
| **Рецепты** | Личная библиотека пользователя: состав на всю кастрюлю, выход готового блюда (учёт уварки/ужарки), порции, КБЖУ на 100 г считаются автоматически. |
| **Холодильник** | «Кастрюля» — конкретная готовка с **фактическим** составом и весом. Остаток уменьшается при «съедено». Резерв под планы, ручная правка остатка, «выбросить остаток», архив с журналом. |
| **План / дневник** | Запись = приём пищи + блюдо + вес. Три статуса: план по шаблону → план из кастрюли (после готовки привязывается сам) → факт. КБЖУ считаются по реальной кастрюле, если она есть. |
| **Покупки** | Сумма ингредиентов по ещё не приготовленным планам за период; масштаб по «числу едоков». |
| **Сервис** | FastAPI + async SQLAlchemy + PostgreSQL, Alembic, JWT, слои repository/service, 22 интеграционных теста. |

Архитектура бэкенда хорошая: слои разделены честно, доменные ошибки маппятся в HTTP в одном месте, изоляция данных пользователей покрыта тестами. Идея «рецепт-шаблон ↔ кастрюля с фактическим составом» сильная. В обычных трекерах такого нет, а для домашней кухни это главное.

### 3.2. Баг: приготовленная кастрюля «съедает» все будущие планы — ✅ исправлено
`reattach_template_plans` привязывал к новой кастрюле **все** планы рецепта, без учёта дат и вместимости. Пример: борщ на понедельник и на следующее воскресенье, варите в понедельник — воскресный борщ пропадал из списка покупок, хотя кастрюлю к тому времени уже доедят.

**Как теперь (ветка `fix/plans-and-cleanup`):**
- При готовке к кастрюле привязываются только планы **начиная с сегодняшнего дня**, по порядку (дата → завтрак/обед/ужин/перекус), пока они помещаются в выход блюда. Остальные остаются «надо приготовить» и попадают в покупки.
- Новый план по блюду, которое уже стоит в холодильнике, сразу резервируется из кастрюли, если свободного хватает. Раньше он уходил в покупки.
- Когда кастрюля убывает («съели больше», ручная правка остатка), поздние планы, которым уже не хватает, автоматически снова становятся «надо приготовить».
- «Сколько человек едят» теперь означает одно и то же везде: все едят одинаковую порцию. Из кастрюли и в покупки уходит `порция × едоки`, личные КБЖУ считаются на одну порцию.

## 4. Что сделано в этой итерации

- **Новый веб-интерфейс** (`web/`) на Vue 3 вместо Streamlit. Работает без Node и сборки: библиотека лежит в репозитории, а FastAPI раздаёт UI по адресу `/app/` (один процесс, без CORS). Адаптивный: на телефоне есть нижнее меню, удобно открывать список покупок в магазине.
  - **План** — неделя на 7 колонок × 4 приёма пищи, у каждого дня ккал/БЖУ и полоска цели; добавление сразу на несколько дней; «скопировать прошлую неделю»; ссылка на покупки за эту неделю.
  - **День** — детально, с личными КБЖУ против цели и подсказкой, сколько ещё можно съесть и сколько не хватает белка.
  - **Покупки** — группировка по категориям, отметки «куплено», копирование текстом, CSV, быстрые периоды.
  - **Холодильник** — остаток и резерв под планы, правка остатка, фактический состав, «выбросить», безопасное удаление с проверкой дневника, архив.
  - **Рецепты** — создание и правка с живым пересчётом КБЖУ на 100 г, «приготовить» с фактическим составом.
  - **Продукты** — версии КБЖУ по производителям, откат, проверка по Атвотеру прямо при вводе.
  - **Профиль** — цели КБЖУ (пока в браузере), тема.
- **Бэкенд:**
  - готовые продукты в плане (`DiaryLog.variant_id`, миграция `0004`), в том числе в списке покупок;
  - `GET /diary/range` для недели;
  - `POST /diary/{id}/detach` (метод сервиса уже был, не хватало эндпоинта);
  - категории в списке покупок;
  - 2 новых теста.
- Streamlit-UI удалён (после перехода на новый интерфейс).

### Этап 2 — семья ✅ сделано (ветка `feature/family`, миграция `0006`)
```
Household ─┬─ Member (имя, привязанный User или «без аккаунта» для ребёнка, цели КБЖУ)
           ├─ Recipe, CookingLog (холодильник общий)
           └─ MealPlanItem (дата, приём пищи, блюдо | готовый продукт)
                 └─ Portion (member_id, вес, статус: план/съедено)
```
- План составляется один раз на семью. Порции по людям: «папа 350 г, ребёнок 200 г».
- Список покупок = сумма порций. Это честнее, чем `servings_multiplier`, а сам множитель уходит.
- Личные КБЖУ = порции конкретного члена семьи; цели хранятся на сервере.
- Каждый отмечает «съел» за себя, кастрюля списывается общая.
- Справочник продуктов остаётся общим, рецепты переезжают с `user_id` на `household_id`.

Как получилось:
- `Household` + `HouseholdMember` (с аккаунтом или без), цели КБЖУ на сервере. Семья создаётся при первом входе; второй взрослый вступает по 8-значному коду, и всё, что он успел завести, переезжает в общую семью.
- `MealItem` (блюдо на приём пищи) + `MealPortion` (кто и сколько). Порция без человека — **гость**: учитывается в кастрюле и покупках, но ничьих КБЖУ не трогает.
- «Съел» отмечается **по порции** (вес по факту) или «все поели» разом. Списание из кастрюли хранится на порции (`eaten_from_pot_id`), поэтому отмена «съедено» и удаление возвращают вес точно туда, откуда взяли.
- Все правила холодильника из этапа 1 (резерв с сегодняшнего дня по вместимости, освобождение поздних блюд, когда кастрюля убывает) теперь работают по сумме несъеденных порций.
- Миграция переносит старый дневник: каждой записи — блюдо с порцией пользователя, а «+N едоков» превращаются в порции-гостей. Откат обратно в `diary_logs` тоже проверен.
- API: `/household` (состав, цели, код, вступление), `/plan` (блюда и порции, «съел», перенос). Старый `/diary` удалён.
- UI: страница «Семья», переключатель «чьи КБЖУ» в плане и дне, карточка блюда с порциями и отметками.

Что сознательно не сделано (кандидаты на потом): выход из семьи и роли (кто может редактировать), перетаскивание блюд мышью, история изменения целей.
